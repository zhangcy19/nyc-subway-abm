# 第二轮怎么改：文献给出的实际建议

核查日期：2026-10-12。以下是设计参考，不代表这些方法在我们的纽约地铁数据上已经有效。多数是预印本；没有把作者摘要中的“提升”当成独立复验结论。

最值得试的是 **给 LLM 看站点自己的历史、根据训练误差校准，再检查它比不用 LLM 多带来了什么**。单纯加 agent 数、加角色描述或多调用 API，没有充分理由保证准确率上升。

## 首轮为什么可能没有提升

- 干天被程序固定为继续原计划，LLM 基本没有发挥空间；干天结果主要反映基线好不好。
- 所有站点共用少量天气策略，输入没有站点自己的最近走势。这样的 LLM 很难预测不同站点的上下班、上学和周末差异。
- 8 月的学生需求和 9 月开学后的需求不同。只让 LLM 判断雨天是否出门，解决不了出行规模本身的变化。
- 人物的弹性、推迟回流率大多是假设。输出听起来像真实乘客，也不等于这些概率接近真实人群。
- 暴雨属于训练期没有出现的情境。给普通雨天的少量例子，不能自然保证极端情境准确。

以上是针对现有设计的解释和待检验假设，不是已经完成的因果归因。

## 第二轮建议先做这些

1. **先把普通天气跑明白。** 保留按时间先后训练、验证、测试；分别报告无雨、小雨、中雨和高峰。原 9 月 22–30 日已经看过结果，再用它评估改版，应写“回顾性比较”，不能称全新盲测。可用更早的普通天气窗口做滚动评价，注明方法开发仍已看过整个数据背景。
2. **共同升级输入。** 每个模型都拿到相同的过去数据：同站点的历史时段基线、截至预测时点的最近趋势、票种份额、星期/小时、天气数值。当天实际天气只能支持历史条件检验；没有天气预报时，不能说是提前天气预测。
3. **检索少而相关的实例。** 优先同站点、同星期类型、同小时，再看天气相似度；只从过去训练库取，保留实例 ID。检索近邻本身也要作为不用 LLM 的对照。如果近邻已经够好，LLM 不一定值得额外成本。
4. **让校准有数值锚点。** 先拟合简单季节/时段模型，再让 LLM 建议有界修正、群体策略或推迟安排；只在训练和验证反馈中改。加入“相同策略经过数值校准、但不经 LLM 改写”的对照，区分校准与 LLM 的贡献。
5. **逐个模块检查。** 相同站点、预测时间和基线下，比较基础 LLM、加检索、加近期记忆、加校准、去掉 LLM 的版本。先用小样本选值得扩展的方向；主结果对齐相同数据行，再按日期成块比较误差，避免把同一场天气下的站点小时当成独立事件。
6. **agent 数放后面。** 数量变化先共用同一份策略/人物分布与总权重，隔离模拟分辨率；独立重采样策略的变化另列为 API 随机性。更多代表 agent 不会自动创造更多真实信息。
