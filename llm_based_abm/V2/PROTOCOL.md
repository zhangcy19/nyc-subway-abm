# 第二轮：先找到问题，再比较改进

预算上限为 2,100,000 token：正常响应按 API 报告量记账，未返回 usage 的失败请求按预留量保守记账，格式修复也计入。先跑一天检查格式与模拟，再继续；完整缓存可免费重放，不需要花完额度。

第一轮有两个明显限制：晴天策略被固定；所有站点共享八种天气策略。第二轮让 LLM 读取站点历史和近期变化，输出分站点、群体、六小时时段的策略。它可以改变计划出行需求，也可以继续、延迟一小时、换方式或取消。Mesa 保留每个站点四个群体的延迟状态，延迟出行的返回率固定为 0.6。没有真实个体出行链，所以这些状态仍是群体模拟假设。

## 时间和站点

- 训练：8 月 1 日至 9 月 7 日。选取四个 borough 各三个训练期覆盖率足够的站点，排除第一轮 12 站；按训练期客流高、中、低位置选择。
- 反馈：9 月 8–11 日。选择数值模型正则化强度、拟合 LLM 策略校准和反馈摘要。
- 验证：9 月 12–14 日。只用于选择混合权重；权重选定后冻结。
- 回顾性测试：9 月 15–30 日，分别报告普通天气、干燥、轻雨、中雨、极端雨。

新站点此前没有查看未来预测误差，但整个城市的 9 月天气和第一轮部分日期的客流结果已经看过。因此这是固定新划分的回顾性评估，不能称全新独立盲测。新数据到来后才做真正的外部检验。不根据测试结果再次调整模型。

## 预测任务

每天零点一次预测随后 24 小时。只能读取零点以前已完成的客流；不能使用当天真实客流做滚动更新。当天的实测天气作为已知条件供所有模型使用，因此是**天气条件下的历史预测**，不是评估天气预报本身。晚间延迟可以流入第二天；第一天 pending=0。各方法使用相同时间覆盖。

## 比较方法

1. 周周期朴素模型：一周前同小时客流。
2. 分站点星期/小时均值：训练历史加 September 近期权重。
3. 数值模型：Ridge，使用周期均值、前一天/前一周客流、天气、站点、星期、小时。正则化候选只在反馈期比较。
4. 纯历史检索：从训练期检索三个相近日，将其时段残差加权应用在数值基线上，不调用 LLM。
5. 动态 LLM：数值基线、站点/群体概况、前一天实际客流、天气；zero 模式不提供案例。
6. 检索 LLM：同样输入，加三个训练期相似日的群体时段残差。
7. 校准混合：对检索 LLM 用反馈期拟合偏差修正，以验证期确定 LLM 与数值基线的混合权重。允许权重为 0；如果 LLM 不增加价值就保留数值预测。
8. 反馈 critic：另一次 LLM 请求读取反馈期的分站点/群体/时段真实误差，提出 0.75–1.25 的活动倍率修正，随后冻结。它不能读取验证或测试真值。保留纯统计偏差修正作为对照；同时报告 critic 单独版本和验证期选权重的混合版本。

两种动态 LLM 各两次独立请求样本，反馈/验证用第一样本，测试两次全部报告；不能用测试表现挑样本。每个请求批量包含一个 borough 的三站；每站四个群体、四个时段。不同方法读取同一版历史表。群体是票种代理，不是完整社会属性；老人/残疾人源数据仍合并。

总客流使用原始 station totals。票种缺失在历史需求分配中按零贡献处理，原始缺失群体观测不用于群体误差。群体计划质量归一化到独立站点总预测。`activity_multiplier` 和动作概率无法仅靠客流唯一识别，动作解释不能当成已证实的真实行为。

主指标为总客流 WAPE（总绝对误差 / 总实际客流），同时给 RMSE、总量偏差、分站点和分群体误差。提供分日配对误差和 day-block bootstrap，避免把同一场雨的很多小时当成很多独立极端事件。

## 解释这组对照时

zero-shot 指提示里没有相似日示例，仍输入训练得到的数值基线和过去真实客流。反馈 critic 有 192 个站点×群体×时段倍率，而统计校准只有 12 个站点倍率；两者校准粒度不同。因此它们比较的是完整配置，不能将差距单独归因于 LLM。后续若要验证 critic 本身的价值，应增加同样 192 格、相同约束与收缩的纯统计校准对照。

相似日群体比率目前用已观测客流作分子、整个时段预测量作分母；部分小时缺失时，两者覆盖不一致，会让实例比率偏低。测试窗口检索曝光中，学生/Fair Fare/老人残障分别有 34.5%/26.5%/39.4% 属于这种情况，受影响实例相对“分母仅保留已观测小时”口径的比率中位偏低 4.2%/9.0%/8.2%。这是输入实例偏差，不能量化为预测误差贡献。本轮保留已冻结模型与原响应，后续版本应统一分子、分母观察小时口径，再在新数据上评价。

执行时原 2,000,000 保守额度暂停了最后 6 个格式修复批次；已有响应实际报告约 181 万，另约 17 万是失败请求预留。按照已授权的必要预算扩展，上限调整为 2,100,000，仅补完预先定义的比较，没有新增模型或利用测试误差改变参数。
