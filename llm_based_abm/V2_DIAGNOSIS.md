# 为什么首轮 LLM 没有稳定提升，下一轮怎么改

首轮不能概括成“LLM 没用”：**普通天气已经有改善，极端暴雨减量过头，把整体优势抵消了；干天气下，代码又直接禁止 LLM 改需求。** 下一轮应先让模型读到真实站点状态，再检查这些信息能否带来增益，不是单纯增加 agent 和调用次数。

以下数字重新读取现有 `results/predictions.csv.gz`、`weather_metrics.csv`、`metrics.csv` 和 `action_shares.csv` 计算，没有新调用 API，也没有改写首轮预测。WAPE = 站点小时绝对误差之和 / 同批真实客流之和。LLM ABM 使用每站 10 个代表 agent，报告三次策略生成的误差均值；群体预测先加成站点总数，真实值使用独立记录的站点总客流。

## 1. 普通天气其实已有提升

仍使用首轮 9 月 22–30 日检验窗口，仅按天气筛选。

| 模型 | 非极端天气合计 | 干天气 | 小雨/近期有雨 | 中等降雨 | 极端降雨 |
|---|---:|---:|---:|---:|---:|
| 季节校正基线 | 20.65% | 16.44% | 24.57% | 34.80% | 24.35% |
| Rule-based | 19.73% | 16.44% | 23.02% | 29.13% | **21.53%** |
| LLM ABM zero-shot | 18.51% | 16.58% | 20.93% | 19.93% | 31.26% |
| LLM ABM few-shot | 19.40% | 16.50% | 23.02% | 21.76% | 30.12% |
| LLM 直接预测 few-shot | 18.43% | 16.44% | 20.93% | 20.07% | 32.16% |

非极端包含干、小雨、中雨，共 2,364 个站点小时；其中干 1,164、小雨 1,068、中雨 132。极端另有 227 个站点小时。不同天气客流量不同，表里的合计不是四列误差的简单平均。

Zero-shot ABM 在普通天气比规则减少约 **1.23 个百分点**，但 few-shot 没有继续改善。直接预测也能达到接近结果，说明现在的 ABM 部分还没有表现出明显额外价值。这些都是同一批旧测试数据的事后诊断，不能当作新架构的独立验证。

## 2. 核心问题来自模型能看到什么、能做什么

**干天气的误差根本不是 LLM 在预测。** `model.py` 的 `validate_policy()` 把 dry 强制设为 `[1,0,0,0]`，所以当期预测完全跟随季节基线。LLM 的小幅区别只来自上一小时推迟客流的回流。干天气真实客流比基线合计高 **8.02%**，规则、直接 LLM 都少预测 **7.42%**；增加提示或 agent 无法修复这个被写死的入口。

**同一种雨情境，所有站点、所有日期共用一套概率。** LLM 只看四种固定雨量样例和 peak/offpeak；看不到实际逐小时雨量、站点名或属性、最近客流、上一天/周的走势、预测误差。一个刚开始下雨的站点和一个已经降雨六小时的站点，可能拿到相同策略。地图上的差异来自各站历史基线与票种构成，不是 LLM 理解了空间。

**LLM 对 extreme 的损失估计过大。** 用同批数据比较“真实总量 / 季节基线”和“预测总量 / 季节基线”：

| 天气 | 真实 / 基线 | Zero-shot ABM / 基线 | Few-shot ABM / 基线 |
|---|---:|---:|---:|
| 干 | 1.080 | 1.002 | 1.001 |
| 小雨 | 0.850 | 0.922 | 0.976 |
| 中雨 | 0.743 | 0.778 | 0.817 |
| 极端 | 0.873 | 0.637 | 0.714 |

极端时段 zero-shot 少预测真实客流 **27.03%**，few-shot 少预测 **18.21%**。例如 zero-shot 的极端策略平均约 51.90% 继续、20.51% 推迟、16.40% 改方式、11.19% 取消，再叠加只有 60% 的推迟需求回流，长期留存约 64.20%。这解释了数值怎么偏低，但不能证明真实乘客采取了这些行为。

**Few-shot 示例太粗，也不能唯一决定四种行为。** 示例只有 8 月按天气、高峰、票种汇总的 16 条“真实 / 基线”比例，没有一条 extreme；小雨高峰的 general 比例为 1.043，中雨高峰为 1.062。当前 ABM 只能削减当期计划需求，再加固定的一小时回流，不能直接产生新增地铁需求。LLM 接到大于 1 的比例也无法自由表达。此外，客流比例同时包含基线误差、日期构成和天气，不能把它完全归因于天气，更不能由一个比例辨认“改方式”和“取消”各有多少。

**增加 agent 没增加信息。** 每站 5/10/20 个是同一批需求质量的不同分割；每组权重仍合计 1，平均假设灵活度仍为 0.5。Mesa 用概率期望直接求和，未使用随机逐人决策、互动或学习。三次重复的差别主要是 API 策略生成变化，而不是三场天气或三个独立人群。因此代理数量本身不应被期待为提高预测的主手段。

**学生的问题主要还在时间基线。** 开学后的校正倍率在 12 站约为 3.02–8.92 倍，但学生组 WAPE 仍约 64%（季节基线 64.13%、zero-shot 64.45%、few-shot 64.52%）。一个全天通用的倍率很难恢复开学后的上学/放学时间形状。票种也只是人群代理标签：老人和残障仍无法从源数据分开，缺失票种并不一定代表零人。

## 3. 更值得尝试的新架构

建议按“真实数据先建立可用的预测，再让 LLM 判断如何修正”的顺序增加功能。

1. **动态基线。** 使用站点、小时、星期、票种、连续雨量，以及预测时已经可见的过去 1/24/168 小时客流。先做季节朴素预测、可解释回归或树模型。这一步不付 API 费，却能检查“新增近期客流信息”本身有多大贡献。
2. **检索相似历史。** 为当前站点、时段、群体检索预测时刻以前的类似记录，提供实际雨量、过去客流、基线预测、历史真实值和误差；不再只给 16 个全城汇总比例。每条记忆保留时间，检索禁止看到目标时段及未来。
3. **让 LLM 输出可校准修正。** LLM 判断基线偏高还是偏低、给有限范围的需求修正及群体行动概率。普通干天气也允许修正，允许地铁替代其他交通带来的需求增长。只用校准集确定修正强度和权重；不靠测试误差反复改提示。概率总和、群体加总和推迟队列仍由 Python 实现。
4. **保留逐站群体状态。** Agent 记住待出发需求、最近误差、风险/出发灵活度等状态；依据真实时序改变策略。延期不必固定为一小时，可在校准阶段比较几个简单分布。仅凭客流仍无法确认取消/换方式的真实份额，这部分只能作为情境假设。
5. **滚动反馈，但明确时点。** 例如预测下一小时，只能用上一小时已经到达的客流与天气。在真实部署中若数据有一天延迟，不能假设上一小时立即可用。回测可先做“零延迟的一小时预测”假设，并另测 24 小时延迟，不把两者混为同一任务。

更复杂的多 agent 讨论、planning/review、记忆总结可以随后测试；如果动态基线已经很好，LLM 只需要解释和有限修正。每项高级模块都应有对应的去除模块对照：**动态基线 → 基线加检索但不用 LLM → LLM 修正 → LLM 加记忆/反馈 → 群体 ABM**。各对照必须看到相同的过去数据、面对相同预测时点；不允许只有 LLM 获得近期客流却宣称提升来自语言推理。

## 4. 现有数据如何继续用

现有 8–9 月仍能做一般天气、滚动预测和不同模块对照，不必等新暴雨。可以从较早日期训练，在后续多个日期滚动检验；站点规模也可以扩展，但先固定方法再扩站。

需要如实区分两层“留出”：某个 V2 拟合过程可以没有使用后续日期的目标值，但整个项目早已使用完整 8 月建首轮基线和选站，并读取完整 9 月测试结果。**重新切出 8 月某些日期不是项目级全新、从未看过的测试集；9 月 22–30 日更不能再次称为一次性未触碰检验。** 新实验可以报告“旧数据上的重新划分/探索性滚动回测”，后续拿到新月份再做真正冻结后的最终验证。

天气分类也最好补充纯当前雨量与连续雨量的报告。现有 light 包括“本小时无雨、但过去六小时有雨”，不能把这些时段都称为本小时小雨。极端雨期里可能还混合服务扰动和新闻影响，没有服务数据时，不凭模型推理把偏差解释成真实停运。

## 5. 预算优先花在哪

200 万 token 足够做完整架构对照，但应先用少量站点、固定时间块试跑，检查新增状态信息真的进入模型且结果合法，再扩展站点和重复。缓存相同提示、保存实际响应和使用量，用确定性的 Python 重放 agent 后续过程；无需每个 agent、每小时都重新调用。

判断是否值得扩跑，优先看逐日和逐站配对误差、群体误差、系统性高估/低估，以及是否超过“相同信息的非 LLM 动态基线”。多个站点同日共享天气，不宜把几千条小时记录当作几千场独立天气事件；3 次 API 生成也不等于 3 次独立验证。
